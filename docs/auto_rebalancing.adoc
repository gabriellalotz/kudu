[[auto_rebalancing]]
= Apache Kudu Automatic Cluster Rebalancing
:author: Kudu Team
:imagesdir: ./images
:icons: font
:toc: left
:toclevels: 3
:doctype: book
:backend: html5
:sectlinks:

include::top.adoc[tags=version]

Kudu masters can run two background tasks that keep the cluster balanced
without operator involvement:

* The _auto-rebalancer_ moves tablet replicas between tablet servers so that
  each table, and the cluster as a whole, has roughly the same number of
  replicas on every tablet server. It can also balance each range partition of
  a table separately, with `--auto_rebalancing_enable_range_rebalancing`.
  It is enabled with `--auto_rebalancing_enabled`.
* The _auto-leader-rebalancer_ moves Raft leadership between the existing
  replicas of each tablet so that leader replicas are spread evenly across
  tablet servers. It doesn't move any data. It is enabled with
  `--auto_leader_rebalancing_enabled`.

When enabled, both tasks run on every master, but only the leader master does
any rebalancing work; on the other masters they stay idle until their master
becomes the leader. `--auto_rebalancing_enabled` and
`--auto_leader_rebalancing_enabled` can be changed at runtime with
`kudu master set_flag`, once the masters have the extra flag described in
<<auto_rebalancing_prerequisites,Prerequisites>>. Since the leader master can
change, set them on every master, for example with
`kudu master set_flag_for_all`.

The two tasks are independent and can be enabled separately, but they work
well together. Moving a replica can change which tablet server leads a tablet,
so the leader distribution may drift while the auto-rebalancer is working. The
auto-leader-rebalancer evens it out again in a later round.

[[auto_rebalancing_cli]]
== Relation to the CLI rebalancing tool

The `kudu cluster rebalance` tool described in
link:administration.html#rebalancer_tool[Running the tablet rebalancing tool]
and the auto-rebalancer use the same rebalancing algorithms and the same way of
moving replicas: the source replica is marked for replacement, a new replica is
added on the destination tablet server, and the source replica is evicted once
the new one has caught up. The difference is how they run. The CLI tool is a
one-off session that runs until the cluster is balanced (or until
`--max_run_time_sec` passes), while the auto-rebalancer keeps checking the
cluster at a fixed interval and makes a small batch of moves each time.

The CLI tool also covers a few cases the auto-rebalancer doesn't:

* Moving all replicas off particular tablet servers when
  link:administration.html#tablet_server_decommissioning[decommissioning tablet servers].
  This is done with `--move_replicas_from_ignored_tservers`, with the tablet
  servers to empty listed in `--ignored_tservers`.
* Running on a cluster where some tablet servers are down, by listing them in
  `--ignored_tservers`. The tool then works as if those tablet servers and
  their replicas weren't there. Without that, it refuses to run on such a
  cluster.
* Reporting how unbalanced the cluster is without moving anything, with
  `--report_only`. Add `--output_replica_distribution_details` to also get the
  replica distribution per table and per tablet server.

On an existing cluster with a lot of skew, it's a good idea to run the CLI tool
once before enabling the auto-rebalancer, so the cluster starts out balanced
and the auto-rebalancer only has to deal with smaller changes.

The CLI tool only moves replicas; it doesn't rebalance leaders (see
link:https://issues.apache.org/jira/browse/KUDU-3833[KUDU-3833]).

[[auto_rebalancing_cli_conflict]]
=== Running CLI-based and automatic rebalancing at the same time

Running the CLI rebalancing tool while the auto-rebalancer is enabled isn't
recommended. Neither knows about the moves the other one has scheduled, so they
may both try to move replicas of the same tablet, or together run more
concurrent moves on a tablet server than either one's per-server limit allows.
Before running `kudu cluster rebalance`, disable the auto-rebalancer on all
masters and enable it again once the tool has finished:

[source,bash]
----
sudo -u kudu kudu master set_flag_for_all <master_addresses> auto_rebalancing_enabled false
sudo -u kudu kudu cluster rebalance <master_addresses>
sudo -u kudu kudu master set_flag_for_all <master_addresses> auto_rebalancing_enabled true
----

Disabling the auto-rebalancer takes effect at the start of its next round.
Moves it has already scheduled aren't cancelled and keep going until they
finish.

[[auto_rebalancing_prerequisites]]
== Prerequisites

`--auto_rebalancing_enabled` and `--auto_leader_rebalancing_enabled` have been
experimental since they were added, and they still are in Kudu 1.19.0, so the
masters also need `--unlock_experimental_flags`. Without it, a master started
with either flag set to `true` refuses to start, and setting either one to
`true` with `kudu master set_flag` is rejected.

The auto-rebalancer requires the 3-4-3 replica management scheme, that is,
`--raft_prepare_replacement_before_eviction=true` on the masters. A master
started with `--auto_rebalancing_enabled=true` and
`--raft_prepare_replacement_before_eviction=false` fails flag validation and
doesn't start.

The auto-rebalancer only makes moves when every live tablet server is
available for placement and no tablet has a replica on a tablet server that is
down. Otherwise the round is skipped. This happens while a live tablet server
is in maintenance mode (see below), and while a tablet server is down and its
replicas haven't been replaced on other tablet servers yet. Unlike the CLI
tool, the auto-rebalancer has no option to ignore such tablet servers.

[[auto_rebalancing_flags]]
== Configuration

Both tasks are configured with flags on the masters. See the
link:configuration_reference.html[configuration reference] for the flags, their
default values, and whether they can be changed at runtime.

[[auto_rebalancing_algorithm]]
== How the auto-leader-rebalancer picks moves

Each round has two passes. The per-table pass spreads each table's leader
replicas evenly across the tablet servers hosting the table's replicas. When it
moves leadership of a tablet, it hands it to the follower whose tablet server
has the lowest ratio of leaders to replicas for that table. The global pass
then moves leadership from tablet servers hosting the most leader replicas
across all tables to the ones hosting the fewest, without making any single
table uneven again. The global pass only runs in rounds where the per-table
pass had nothing left to do; otherwise it's postponed to a later round. Tables
with a replication factor of 1 are skipped, since there's no other replica to
hand leadership to.

[[auto_rebalancing_maintenance_mode]]
== Tablet servers in maintenance mode

The two tasks treat tablet servers in
link:administration.html#minimizing_cluster_disruption_during_temporary_single_ts_downtime[maintenance mode]
differently:

* The auto-rebalancer doesn't make any moves while a live tablet server is in
  maintenance mode. Each round is skipped until the tablet server leaves
  maintenance mode, so replicas don't have to be moved back once it returns.
* The auto-leader-rebalancer never moves leadership onto a tablet server in
  maintenance mode. Such a tablet server can still give leaders away if it
  hosts more than its share of leader replicas: of a single table in the
  per-table pass, or across all tables in the global pass, which works out that
  share from the other tablet servers only. Neither pass moves all leaders away
  from it. To do that before taking a tablet server down, use
  `kudu tserver quiesce start` as described in
  link:administration.html#rolling_restart[Orchestrating a rolling restart].

[[auto_rebalancing_metrics]]
== Metrics

The masters expose the following counters for the two tasks. Since the actual
rebalancing work is done only by the leader master, only the leader master
provides valid readings of these counters.

Auto-rebalancer counters:

`auto_rebalancer_follower_moves_scheduled`::
Replica moves scheduled where the source replica was a follower.
`auto_rebalancer_leader_moves_scheduled`::
Replica moves scheduled where the source replica was the leader, because no
follower could be moved instead. Each of these moves also changes the tablet's
leader, so clients writing to it have to find the new leader.
`auto_rebalancer_rounds_completed`::
Rounds that ran to the end, including waiting for their moves to finish.
Skipped rounds, for example while a tablet server is in maintenance mode, don't
count. If the auto-rebalancer is enabled but this counter isn't growing, check
the leader master's log for the reason.

Auto-leader-rebalancer counters:

`auto_leader_rebalancer_moves_scheduled`::
Leader transfers attempted, across both passes. A transfer counts once it
passes the pre-flight checks, right before its `LeaderStepDown` request is
sent. This counter is always the sum of the next two.
`auto_leader_rebalancer_moves_completed`::
Leader transfers accepted by the tablet server.
`auto_leader_rebalancer_moves_failed`::
Leader transfers that failed or were rejected by the tablet server.
`auto_leader_rebalancer_rounds_completed`::
Rounds that ran to the end.
`auto_leader_rebalancer_global_pass_skipped`::
Rounds where the global pass was postponed because the per-table pass still
had work to do. If it grows every round for a long time, the per-table pass
keeps finding new work (for example because of frequent leader elections) and
the global pass never gets to run.
`auto_leader_rebalancer_task_errors`::
Rounds that failed with an unexpected error. This is a warning-level metric
and the best one to alert on if the task seems stuck.

Cluster-wide gauges, which are useful whether or not the tasks are enabled:

`cluster_replica_skew`::
The difference between the number of replicas on the tablet server hosting the
most replicas and the one hosting the fewest.
`cluster_leader_skew`::
The same for Raft leaders: the difference between the number of leader
replicas on the tablet server hosting the most and the one hosting the fewest.
Tablet servers running a version that doesn't report its leader count to the
master are left out. If the value stays high while the auto-leader-rebalancer
is enabled, first check whether `auto_leader_rebalancer_moves_failed`,
`auto_leader_rebalancer_task_errors` or
`auto_leader_rebalancer_global_pass_skipped` keep growing, and look at the
leader master's log. If they don't, the task probably can't keep up; consider
lowering `--auto_leader_rebalancing_interval_seconds` or raising
`--leader_rebalancing_max_moves_per_round`.
